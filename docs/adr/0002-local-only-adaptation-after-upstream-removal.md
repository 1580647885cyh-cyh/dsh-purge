# 上游 1.1.71 删除后：只在本地做 DSH 适配

用户保留的 1.1.71 含完整内容（完整 AI 预设），是本项目唯一的内容基线。上游
`YuJunZhiXue/dsh-purge` 已删除 1.1.71（Releases 与 tags 都是 404，现存 tag 从 `v1.1.73` 起），
且其后的版本内容与本基线不等价。因此宿主（DeepSeek Harness）的后续适配由本项目本地完成。

本决策与 [ADR-0001](0001-maintain-local-1.1.71-compatibility.md) 是同一条线上的两段：
0001 决定"以 1.1.71 为保护基线、只修兼容缺陷"，本 ADR 补上"上游已不可用之后，这些缺陷由谁修、按什么边界修"。

## 决策

1. **内容基线唯一**：`presets/**`、`skills/**`、内嵌提示词（`lib/asset-table.js` 的 SLOT_ROWS）、
   `lib/default-prompt-inject*`、`lib/capability-protocol.js` 的正文，以 1.1.71 为准且只增不减。
   版本号与远程更新锁永久保持（`lib/local-version-lock.js`，无绕过开关）。
2. **适配只在本地自研**：上游 `v1.1.73+` 只作**线索**，用于理解"宿主改了什么"；
   不整包引入、不 cherry-pick 上游文件。理由：上游 1.1.71 已不存在，任何跟随都不可回退，
   且后续版本的内容与本基线不等价。
3. **适配只许改机制面**：锚点/匹配式、状态词表与判定、宿主发现与布局、装配顺序、
   换包与重启的时序、报告口径。**不许改能力面**（工具集合、预设插件行、技能清单、提示词正文）。
4. **每项适配必须先在本机复现**：复现不到就不做（对齐 ADR-0001「独立发现的问题须能复现」）。

## 后果

- 上游的新功能（红队中文化、面板改动、安装流程优化）我们**不跟**，也不该为它们付维护成本。
- 适配成本全部由本项目承担，所以基础设施只投"能降低每轮适配成本"的那一类，
  其余架构改造不做（清单见 `docs/architecture-review-2026-11-03.md` 的 Tier 3）。
- 判断一项工作该不该做，用一条规则：**它能消掉一次我们在本机真的复现过的宿主缺陷吗？**

## 守卫

| 守卫 | 拦住什么 |
| --- | --- |
| `tests/archive/original-1.1.71.test.js` | 原版备份被改动 / 当前树丢掉原版文件 / 工具·预设行·技能变少 / 内嵌提示词改一个字 |
| `docs/original-1.1.71.sha256.json` | 原版 108 文件的哈希台账 |
| `docs/original-1.1.71.capability.json` | 能力面指纹（56 工具 / 25 预设行 / 22 技能 / 提示词 original+current 哈希） |
| `lib/local-version-lock.js` | 远程更新、切版本、回滚 |
| `npm run verify` 入口三 | 状态说成功但文件里没有事实（假成功）、状态超前/落后 |

原版备份目录（仓库外）与 `prompt-inject.md.bak` 已设只读。

## 已否决的替代方案

- **跟随上游升级到 1.1.90**：会把不等价（且用户判断为削弱）的内容带进来；1.1.71 已从上游消失，
  升级即不可回退。
- **cherry-pick 上游适配 commit**：单个 commit 也常同时携带文案与能力面改动，
  且会绕过上面的能力守卫；借鉴机制、本地重写更安全。
- **只在 UI 层兼容**：宿主的破坏点集中在加载、装配、换包与重启时序，UI 层拦不住。

## 验收

- 能力面守卫四条全绿，且每条都验证过"会红"（故障对照已跑：改错哈希 / 清单塞不存在的工具 / 塞不存在的文件）。
- 每项适配带一条故障对照（CODING_STANDARDS #6：拔掉**生产路径上的那一处**）。
- `npm run verify` 连续 10 轮通过（口径同 #16）。
